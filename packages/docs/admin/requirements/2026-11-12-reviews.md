# Admin application reviews

## Context

medmate-server already queues pharmacy applications and stores one overall decision per stage. `GET /pharmacy-applications?status=pending_compliance|pending_admin` returns a summary. `GET /pharmacy-applications/{id}` returns the submitted fields and document links. `POST /pharmacy-applications/{id}/compliance-decision` is allowed for an admin or a platform staff account whose subtypes include `compliance`. `POST /pharmacy-applications/{id}/admin-decision` is admin-only and only from `pending_admin`. Reject requires a comment.

The admin portal is still an empty shell, and login always sends `accountType: "admin"`. A compliance account is `accountType: "staff"`, so that person cannot open the portal. This requirement adds a Reviews section for both, and the sign-in choice that lets compliance reach it.

## Scope

- A sign-in choice on the admin login phone step: Platform admin or Compliance.
- A Reviews section in the signed-in shell for an admin or a compliance staff account.
- One list of applications in `pending_compliance` and `pending_admin`.
- A detail screen for one application: every returned field, each stored file, then Approve or Reject when this account can decide that stage.

## Non-goals

- medmate-server, the dispensary portal, and the pharmacy app.
- Letting finance, sales, or support stay signed in.
- Search, filters, pagination, or a second queue.
- Per-field or per-document decisions, review history, or editing the application.
- Removing the onboarding slides, the business-type cards, the business-name field, or the PIN step. The business name is still not sent.
- A new visual system. The screen uses the admin shell and the existing Tailwind tokens.

## Behavior

### Sign-in

On the login phone step, above the mobile number, a radiogroup labelled "Account" offers "Platform admin" and "Compliance". Platform admin is selected by default. The control is hidden on the OTP and PIN steps. Changing the number returns to the phone step with the last choice kept.

Platform admin sends `accountType: "admin"`. Compliance sends `accountType: "staff"`. Send, verify, and PIN login all use that choice.

A successful verify or PIN login is stored only when the account matches the choice. Otherwise the new refresh token is revoked, the session is not stored, and the phone step shows one of these messages:

| Choice | Account | Message |
| --- | --- | --- |
| Platform admin | `staff` with `compliance` | This number is a compliance account. Choose Compliance to sign in. |
| Platform admin | anything else that is not `admin` | This number is not a platform admin. |
| Compliance | `admin` | This number is a platform admin. Choose Platform admin to sign in. |
| Compliance | `staff` without `compliance` | This account cannot review applications. |
| Compliance | anything else | This number is not a compliance account. |

A stored session that is not an admin, and not staff with `compliance`, is cleared and the login screen is shown. Its refresh token is revoked when one is still present.

The sidebar role is "Platform admin" for an admin and "Compliance" for compliance staff. Both see Home and Reviews.

### List

Reviews is a sidebar item labelled "Reviews". Its route is `/reviews`. The page loads `pending_compliance` and `pending_admin` together. Rows are ordered by `submittedAt` ascending, with a missing time last.

Each row shows the pharmacy name, phone, a stage label, and the submitted time. The time is a `time` element whose `dateTime` is the API instant.

| Status | Stage label |
| --- | --- |
| `pending_compliance` | Compliance review |
| `pending_admin` | Final review |

The row's accessible name is the pharmacy name. Activating it opens `/reviews/{pharmacyId}`.

While either request is in flight, the page does not show the empty state. When both succeed and both lists are empty, the page says "No applications are waiting for review." When either request fails, the page shows that problem detail and no rows.

### Detail

`/reviews/{pharmacyId}` stays inside the shell. The shell header stays Reviews, and Reviews stays selected in the sidebar. The page heading is the pharmacy name, with a link back to `/reviews` named "All applications".

The page reads `GET /pharmacy-applications/{id}` and shows every returned field. Empty text is an em dash. Booleans are Yes or No. `businessTypes` is the returned list. Fields are grouped, in this order:

1. Summary: stage or status, phone, email, submitted time.
2. Pharmacy: name, tagline, address, city, state, pincode.
3. Registration: business types, industry, registration type, pharmacy type.
4. Licences: GSTIN, PAN, drug licence number, FSSAI number, trade licence number, TDS, TCS.
5. Billing: pharmacist name, invoice prefix, terms, online orders, self-order kiosk, e-invoicing, loose selling, low-stock alerts.

Documents follow, in the order returned. Slot labels are Logo, GST certificate, PAN card, Drug licence, FSSAI, Trade licence, Pharmacist certificate, and Signature. The first document is selected on load. Choosing another replaces the preview. An image is an `img` whose alt is the slot label. A PDF is an `iframe` titled with the slot label. A path URL is loaded with the session bearer through the admin API client. An absolute `https` URL is used as the preview address and is not requested with a bearer. A failed file read shows the problem detail in the preview.

### Decision

Approve and Reject are shown only when this account can record the current stage.

| Status | Who | Request |
| --- | --- | --- |
| `pending_compliance` | admin, or staff with `compliance` | `POST /pharmacy-applications/{id}/compliance-decision` |
| `pending_admin` | admin | `POST /pharmacy-applications/{id}/admin-decision` |

A compliance account reading `pending_admin` sees the fields and files, no decision buttons, and the sentence "Final review is with admin." Any other status has no decision buttons and the sentence "This application is not waiting for review."

Approve opens a confirmation, then sends `{ "decision": "approve" }` and no comment. Reject reveals a required field named "Rejection comment". A blank comment does not submit and shows "A comment is required." A comment longer than 2000 characters does not submit. With a valid comment, Reject application opens a confirmation, then sends `{ "decision": "reject", "comment": "<trimmed>" }`. The dialog copy is in [2026-11-12-action-confirmations.md](2026-11-12-action-confirmations.md).

A successful decision returns to `/reviews`. A failed decision stays on the detail and shows the problem detail.

## Acceptance criteria

- The default login choice sends `accountType: "admin"`. Choosing Compliance sends `accountType: "staff"`.
- An admin session and a compliance staff session both open the shell and see Reviews. A finance staff verify does not store a session and shows "This account cannot review applications."
- `/reviews` lists both waiting stages, oldest submission first, and an empty pair of lists shows the empty sentence.
- Opening a row shows the returned fields and the first file. A compliance account on `pending_admin` cannot approve or reject.
- Admin Approve on `pending_compliance` posts the compliance decision and returns to the list. Admin Approve on `pending_admin` posts the admin decision. Reject posts the matching decision only after a comment.

## Tests

- `portalAccount.test.ts`: the choice maps to `admin` or `staff`, and each mismatch row above returns its message.
- `AppRouter.test.tsx`: default verify sends `admin`; Compliance verify sends `staff` and shows Reviews; a finance verify stays on login with the refusal message; a compliance session shows the role "Compliance".
- `ReviewsPage.test.tsx`: both statuses are requested, rows show the stage label and the pharmacy name, the empty sentence appears when both lists are empty, and a failure shows the problem detail without rows.
- `ReviewDetailPage.test.tsx`: fields and the first file render; compliance on `pending_admin` has no Approve or Reject; admin Approve posts `compliance-decision` or `admin-decision` for the matching status and returns to `/reviews`; Reject without a comment does not post.
